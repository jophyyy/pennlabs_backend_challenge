# Open-Ended Questions

## 1.

To implement a signup, login and logout, I'd use post routes. Signup would create a new user with a hashed password, login would verify credentials with internal databases while returning a secure session token, and logout would invalidate that secure session token. I think for security, it is essential to never store plaintext passwords. I'd use some form of hashing, like bcrypt. If hackers were to get into the database, they'd see irreversible hashes which prevents simple brute-force attacks. Another security vulnerability could be XSS/CSRF that include a hacker's client-side malicious JavaScript injection. To prevent JavaScript injections to steal session tokens, I'd store session tokens in cookies with attributes of HttpOnly, Secure, and SameSite=Lax. That way, session tokens are not accessible by client-side scripts, only transmittable over encrypted HTTPs, and prevents unauthorized data submission on alternate sites. To implement these security features, I'd use python packages like bcrypt, Flask-login, and Flask-Limiter to prevent overloading and brute-force attacks. We can use existing HTTPs protocol and PennKey's OAuth 2.0 and built in 2-step verification with Duo to handle authentication with everyone's PennKey directly, so holding our own passwords and worrying about hashing is unnecessary. 

## 2.

The way platforms like Reddit allow users to reply to comments indefinitely is nested comment chains. In these cases, each reply functions as a "child" to the "parent" or original comment. To replicate this, I'd create a single Comment table that self-references itself using foreign keys to create replys as "child" functions. I'd name the primary key comment_id so that each original comment is unique. I'd also put club_code so that we know under which clubs the comments are actually under. Then, I'd use author_username to get user info, content to put the comment's body, and created_at to store the datatime of the comment. I can check to see if parent_id exists for every new comment to see if it's a reply or a "root comment". The relationship between club -> comments and user -> comments are both one-to-many. There can be many comments per club and users can have commented multiple time, but these comments are stored under one label. On the other hand, comment -> replies is a one-to-many as there can be many replies per comment. To instantiated these objects, root comments would create a new Comment class that has a new author username, content, and a parent_id=None. Then, it'd be commited to the database. Replies function nearly the same, as replies also creates a Comment class with a new author username and content. The only difference between replies and root comments are parent_ids. Replies will have definied parent_ids, starting with 1 (for replying to the root comment). Grandchildren replies will also have defined parent_ids that point specifically to which reply they're replying to.

## 3.

I think heavy routes that everyone uses are worth caching, such as the GET route to query all available clubs and the GET route to query all available tags. Since both club and tag descriptions rarely change, I think it would be efficient to cache them so that everyday users get faster responses without overloading the actual database. For Cache Invalidation, which happens when a club officer modifies their club's information while our cache hasn't updated, we could delete old cached keys whenever the database receives a POST / PATCH route. Since changes almost always happen when a POST / PATCH happen, it'd be necessary to change the cache when those happen. This would be much more efficient than querying the database everytime for a GET route, as POST/PATCH routes happen much less than general GET routes. If the database were to miss a POST/PATCH route, we could set up a TTL cache, which refreshes the cache after a certain amount of time (I believe a minute or two would be enough). I'd use Flask-Caching to cache and store it in Redis.
